# 05 功能差距与实施计划

> 对标对象：Codex Remote Bridge v4.0.0（本地手机控制 ChatGPT/Codex 的桥接工具）
> 数据来源：2026-08 通过 WebSearch 对 GitHub 开源项目进行功能对标（共 33 个真实项目，详见《04-功能对标分析.xlsx》）
> 结论摘要：ChatGPT Win 在「局域网桥接 + 桌面控制 + 调度 + 安全」方向已相当完整（CDP/App-Server 双通道、SQLite 队列、cron 调度、HTTPS 证书链均为社区前列），主要差距集中在**手机端体验增强**（语音、导出、提示词库）与**能力延伸**（全文搜索、文件传输、屏幕预览），而非核心架构。

---

## 一、功能差距汇总表

| # | 缺失/待增强功能 | 社区主流度（对标项目） | 我们现状 | 优先级 | 建议引入方式 |
|---|---|---|---|---|---|
| 1 | **语音输入（STT）** | 高（LobeChat、OpenAI Translator、OpenClaw 均为标配） | 无：手机端只能键盘打字 | **P0** | 复用浏览器 Web Speech API（零依赖），手机网页端一键语音听写 |
| 2 | **语音输出（TTS）** | 高（LobeChat、OpenAI Translator、Chatbox 均内置） | 无：回复只能看不能听 | **P0** | Web Speech API `speechSynthesis` 播报最终回复/失败原因 |
| 3 | **对话导出（Markdown/文本）** | 高（lencx/ChatGPT 导出 MD/PNG/PDF、Chatbox 一键导出） | 无：只能在线浏览历史 | **P0** | 新增 `/codex/export` 端点，复用现有 `parseCodexThreadHistory` 数据 |
| 4 | **提示词库（Prompt Library）** | 高（Chatbox、lencx/ChatGPT 均有专用库） | 无：每次手打提示词 | **P0** | state.json 增加 `promptLibrary` 字段 + 手机端快捷插入面板 |
| 5 | **定时任务：时区支持** | 中（node-cron、cron-parser、Bull 均支持 timezone） | 部分：cron 解析用本地时区，无 `timezone` 字段 | **P1** | CronParser 增加时区参数（Intl API，零依赖），任务记录增加 `timezone` 字段 |
| 6 | **历史全文搜索** | 中（LibreChat 对话搜索、NextChat 内置搜索） | 无：线程列表只能按名称排序 | **P1** | 新增 `/codex/search` 端点，对会话 jsonl 做受限全文 grep + 高亮 |
| 7 | **通用文件传输（手机⇄电脑）** | 中（RustDesk 文件传输、BilldDesk 文件传输） | 部分：仅手机→电脑图片附件 | **P1** | 扩展附件类型白名单 + 新增 `/codex/download` 受限目录下载 |
| 8 | **屏幕截图/状态预览** | 中（Puppeteer/Playwright 原生截图；RustDesk 实时画面） | 无：手机看不到电脑画面 | P2 | CDP `Page.captureScreenshot` 截图端点，手机端轮询缩略图 |
| 9 | **多用户/RBAC** | 中（Open WebUI、LibreChat、AnythingLLM 均有用户体系） | 无：单 token 全权限 | P2 | 保留单用户定位，暂不引入；可先做 token 分级（只读/读写） |
| 10 | **RAG 知识库** | 高（AnythingLLM、Dify、FastGPT、Open WebUI） | 无 | P2 | 定位不符（我们是控制层非知识平台），长期可选 |
| 11 | **消息平台通道（Telegram 等）** | 中高（OpenClaw 20+ 平台接入） | 无：仅局域网 Web/App | P2 | 可选扩展：Webhook 入站转 `/send`，复用现有 webhook 机制 |
| 12 | **CDP 高级能力（DOM/元素点击/Trace）** | 高（Puppeteer、Playwright、chrome-remote-interface） | 部分：WebSocket 推送 + 简单命令注入 | P2 | 保持零依赖自研，仅参考其协议用法补齐事件订阅 |
| 13 | **多语言扩展（>2 种）** | 高（NextChat、LobeChat i18n 自动化） | 部分：中/英双语 | P2 | 沿用现有 strings 机制扩展，优先级低 |
| 14 | **对话分支/回复引用** | 中（Open WebUI 对话分支、Chatbox 消息引用） | 无 | P2 | 由 Codex 桌面侧能力决定，暂不自行实现 |

### 优先级定义
- **P0**：社区事实标配、当前缺失、且实现成本低（1~3 天/项），直接影响手机端使用体验。
- **P1**：常见刚需，实现成本可控（2~5 天/项），显著提升可用性。
- **P2**：锦上添花或定位延伸，需权衡投入，可排期后续。

## 二、P0 功能引入方案

### 2.1 语音输入（STT）

- **依赖分析**：零新增依赖。Web Speech API（`webkitSpeechRecognition` / `SpeechRecognition`）在手机 Chrome/Edge/Android WebView 均可用；Android WebView 默认支持，iOS 需要用户首次授权麦克风。
- **适配思路**：手机端是单页 `public/index.html`（内联脚本），在消息输入框左侧加麦克风按钮；识别结果填入输入框；失败（权限拒绝/无网络）给出中文 toast，不影响原有键盘输入。
- **最小侵入集成步骤**：
  1. `public/index.html`：新增 `<button id="micBtn">` 与 `speech.js` 风格内联代码（`recognition.lang = 'zh-CN'`，`continuous=false`，`interimResults=true`）。
  2. 监听 `onresult` 将 final transcript 追加到输入框；`onerror` 分支处理 `not-allowed`（提示去浏览器设置开麦克风）。
  3. 桌面端零改动。
- **验证方式**：手机浏览器/Android App 点麦克风说出"帮我写个快排"，确认输入框出现中文文本；拒绝权限时出现明确提示且页面不报错。

### 2.2 语音输出（TTS）

- **依赖分析**：零新增依赖。`speechSynthesis.speak()` 全平台可用；中文音色由系统提供。
- **适配思路**：在助手消息气泡右侧加"朗读"按钮；朗读时高亮气泡、可再次点击停止（`speechSynthesis.cancel()`）；自动朗读可选（设置项）。
- **最小侵入集成步骤**：
  1. `public/index.html`：消息渲染处为 `role === 'assistant'` 的气泡追加喇叭按钮。
  2. 新增 `speak(text)` / `stopSpeak()` 两个函数，使用 `speechSynthesis.getVoices()` 优先选 `zh-CN` 音色。
  3. 页面卸载/切线程时调用 `cancel()` 避免串音。
- **验证方式**：点击历史回复喇叭按钮，Android/iOS 均能中文朗读；连续点击多个气泡不重叠。

### 2.3 对话导出（Markdown）

- **依赖分析**：零新增依赖。数据源已存在——`parseCodexThreadHistory(threadId, limit)`（session-files 通道）与 `historyFromAppServerThread`（app-server 通道）已返回结构化的 `{role, text, attachments, timestamp}` 消息数组。
- **适配思路**：新增只读 GET 端点，把现有历史数据序列化成 Markdown（含标题、元信息、分隔线），浏览器端用 `Blob` 下载；PDF/PNG 涉及分页渲染，成本高，本期只做 Markdown + 纯文本。
- **最小侵入集成步骤**：
  1. `server.js` 路由表新增 `{ method: 'GET', prefix: '/codex/export', handler: handleExport }`。
  2. `handleExport`：校验 `thread` 参数 → 复用 `handleThreadHistory` 的数据获取逻辑 → 组装 Markdown（`# 任务：{name}`、`- 模型/耗时`、逐条 `**你**：` / `**Codex**：`，图片附件输出文件名或内联 `![](/codex/attachment?id=...)`）→ 以 `Content-Disposition: attachment; filename="thread-{id}.md"` 返回。
  3. `public/index.html`：线程菜单加"导出记录"，`location.href = '/codex/export?thread=...'`（带 token 走 cookie 鉴权）。
- **验证方式**：`node --test test/server.test.js` 通过；手机端导出后打开文件，确认消息顺序、代码块、图片引用完整；长会话（120 条上限）不超时。

### 2.4 提示词库（Prompt Library）

- **依赖分析**：零新增依赖。状态已由 `readCodexMiniState/writeCodexMiniState`（state.json）管理，沿用该持久化即可。
- **适配思路**：`state.json` 增加 `promptLibrary: [{id, name, content, createdAt, updatedAt}]`；手机端输入框上方加"提示词"入口，点选后填入输入框（不自动发送，用户可改）。
- **最小侵入集成步骤**：
  1. `server.js`：新增 `handlePromptLibrary`（GET 列表 / POST 增删改），挂到路由表 `{ method: '*', prefix: '/codex/prompts', ... }`。
  2. `src/store`（state.json 读写）不感知字段，`readCodexMiniState`/`writeCodexMiniState` 增加 `promptLibrary` 归一化（过滤非法项、限 200 条）。
  3. `public/index.html`：消息栏上方"提示词"按钮弹出列表，选择后 `input.value = prompt.content`。
- **验证方式**：新增/删除提示词后刷新页面仍在（state.json 持久化）；服务重启后不丢失；旧版本 state.json 无该字段时读取得空数组不报错。

## 三、P1 功能引入方案

### 3.1 定时任务：时区支持

- **依赖分析**：零新增依赖。Node `Intl.DateTimeFormat` 可完成时区换算；`CronParser.nextRun()` 目前用本地时间逐分钟扫描（`src/scheduler/cron.js`），改为"先把目标时区时间转成 UTC 时间戳，再在 UTC 上扫描"即可。
- **适配思路**：调度记录（`createScheduledTaskRecord`）增加可选 `timezone` 字段（默认 `Asia/Shanghai`）；`Scheduler` 计算 `nextRunAt` 时传入时区。
- **最小侵入集成步骤**：
  1. `src/scheduler/cron.js`：`CronParser` 构造增加 `timezone` 选项；`nextRun(afterDate, timezone)` 内部用 `Intl.DateTimeFormat` 把候选时间映射到目标时区做 `_matches` 判断（避免手写时区表）。
  2. `src/scheduler/index.js`：任务创建/更新时校验 `timezone`（`Intl.supportedValuesOf('timeZone')` 包含则合法）；`nextScheduledRunAt` 透传时区。
  3. `public/index.html`：计划编辑表单增加时区下拉（常用 10 个时区 + 跟随本机）。
- **验证方式**：新增计划 `0 9 * * *` + `timezone=America/New_York`，与本地时间对比相差正确；非法时区返回 400；旧任务无 timezone 字段时按默认时区执行（兼容）。

### 3.2 历史全文搜索

- **依赖分析**：零新增依赖。会话文件是 `.codex/sessions/*.jsonl`，已有 `walkFiles` / `readJsonlTailObjects` / `listCodexSessionFiles` 基建。
- **适配思路**：新增只读端点，对会话文件做大小写不敏感的关键词匹配（优先扫描 `user_message` 的 `message` 与 `response_item` 的文本内容），返回 `[{threadId, threadName, matchedAt, snippet}]`，限量（如 50 条）防大文件卡死。
- **最小侵入集成步骤**：
  1. `server.js`：新增 `handleSearch`（GET `/codex/search?q=...&limit=50`），遍历 `listCodexSessionFiles()`，用现有 `readJsonlTailObjects(file, 2MB)` 逐条 JSON 检索并截取上下文片段（复用 `truncateText`）。
  2. 结果命中先读 `readThreadIndex()` 补线程名，排序按 `updatedAt` 倒序。
  3. 路由表挂载；`public/index.html` 线程页顶部加搜索框，展示结果可跳转线程。
- **验证方式**：搜索唯一关键词能定位到对应线程；中文/英文均可用；输入 `<2` 字符返回 400；单次请求耗时 < 2s（受限量）。

### 3.3 通用文件传输（上传/下载）

- **依赖分析**：零新增依赖。现有 `decodeAttachment` 只放行 `image/*`；上传落盘在 `os.tmpdir()/codex-max-uploads`。
- **适配思路**：
  - 上传：附件类型白名单从 `image/*` 扩展到常见文档（pdf/docx/txt/md/code），但仍走「复制到剪贴板 → 粘贴进 Codex」不可行（Codex 只接受图片粘贴），因此**上传方向**改为：生成文件放入 Codex 工作目录（`cwd`）再由用户在下条消息里 `/add` 引用，或直接以 `localImage` 继续走 app-server。
  - 下载：新增 `GET /codex/download?file=<相对路径>&cwd=<project>`，仅允许 `existingProjectCwds()` 内的目录 + 大小上限（如 20MB），返回文件流。
- **最小侵入集成步骤**：
  1. `server.js` 新增 `handleFileDownload`：解析 `cwd` 必须命中项目白名单（复用 `existingProjectCwds`），`file` 用 `path.resolve` 校验前缀防目录穿越，`fs.createReadStream` 流式返回。
  2. `handleEnvironment` 返回的 `capabilities` 增加 `canDownload`；手机端线程/环境面板加"下载文件"入口。
  3. 附件上传保持现状（仅图片），文档类后续再评估 app-server `turn/start` 的 `localImage` 扩展。
- **验证方式**：白名单目录内文件可下载、目录穿越（`../../`）返回 403、超大文件返回 413；环境面板能看到下载入口。

## 四、P2 候选（排期建议）

| 功能 | 引入方式摘要 | 预估工作量 |
|---|---|---|
| 屏幕截图预览 | CDP `Page.captureScreenshot`（CDP 可用时）→ `/codex/screenshot` 缓存缩略图 → 手机端轮询（受 token bucket 限流约束） | 2~3 天 |
| token 分级（只读/读写） | `Security` 支持两个 token 或 scope 字段；写接口校验 scope | 1~2 天 |
| Telegram/消息平台入站 | 复用 `fireWebhook` 出站机制，新增入站 webhook → 转 `/send`（需公网回调，与"局域网直连"定位权衡） | 2~3 天 |
| CDP 事件订阅扩展 | 参考 chrome-remote-interface 的 domain 订阅方式，在 `ws-hub.js` 补充 Runtime/Network 事件转发 | 2~3 天 |
| 多语言扩展 | 沿用 `strings` 中英机制，新增语言包 + `locales_config.xml` | 1~2 天 |

## 五、总体结论

1. **核心架构不需要重构**：CDP/App-Server 双通道控制、SQLite 持久化队列、自研 cron+重试、token bucket 限流、X.509 证书链，在同类开源项目（Codex-Mini、mobile-pc-control 等）中属于领先水平，且"零依赖"定位与 Puppeteer/Playwright/Bull 等重库形成差异化，不建议为对标而引入重依赖。
2. **第一优先级是"手机端体验补全"**：语音输入输出、对话导出、提示词库四项 P0 全部是纯前端/薄端点改动，1 周内可完成，直接对齐 LobeChat/Chatbox/lencx-ChatGPT 的社区标配体验。
3. **需要关注的竞品**：OpenAI 官方 Codex 已于 2026-05 上线"移动端远程连接"（走 ChatGPT 账号 + 安全通道），功能与 ChatGPT Win 重叠但依赖官方账号与云端；本项目"局域网直连、零云端中转、不依赖会员"的定位仍是差异化卖点，建议持续跟踪官方 Automation/Computer Use 能力，评估是否借鉴其"定时任务 + 手机审批"的产品形态。
4. **P1/P2 建议按"使用频次 × 实现成本"排序**：时区支持（低成本高频）→ 全文搜索（中成本高频）→ 文件传输（中成本中频）→ 屏幕预览（中成本中频，受 CDP 可用性限制）。
