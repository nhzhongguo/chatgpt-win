# 03 · 性能优化方案

> 项目：Codex Remote Bridge（v4.0.0）｜ 服务端口：8787 ｜ 审计日期：2026-08-04
> 范围：server.js（约 4800 行）+ src/ 模块 + public/index.html（9088 行）前端 JS
> 测试基线：`node --test test/server.test.js test/codex-app-server.test.js test/behavior.test.js` → **38/38 通过**（Node v24.18.0，401~426ms）

## 一、性能现状分析（架构层结论）

### 1.1 总体架构判断：合理，无系统性缺陷

本项目是"零 npm 依赖"的 Node 原生 HTTP 服务 + JSONRPC/文件驱动的单页控制台。整体架构对性能是**友好**的：

| 维度 | 现状 | 评价 |
|---|---|---|
| 事件循环 | 所有磁盘读取集中在少数同步函数，网络 I/O 全异步 | ✅ 主路径无阻塞风险 |
| 静态资源 | LRU 内存缓存（200 项 / 256KB）+ mtime/size 校验 | ✅ 设计正确，本次仅消除"命中缓存仍 stat"的冗余 |
| 会话文件读取 | 全部走"尾部截断读"（5MB / 512KB / 128MB 分级）+ mtime 缓存 | ✅ 上限可控 |
| 线程列表 | 1.2s TTL 缓存 + 每文件 mtime 缓存 + 64KB 头读取 | ✅ 合理 |
| 队列持久化 | SQLite（better-sqlite3 可选）优先，失败回退 JSON 全量写 | ⚠️ 回退模式有 O(n) 缺陷（已修） |
| WebSocket | 每 5s probe 状态 + 共享帧广播 | ⚠️ 慢客户端无背压保护（已修） |
| 前端轮询 | 4.5s/5s/1.4s 多级轮询，全部带防重入 + `document.hidden` 检查 | ✅ 无泄漏，定时器均有清理路径 |
| 内存缓存 | `boundedSet` LRU（300 项）、各缓存 Map 有上限 | ✅ 无无限增长 |

### 1.2 主要热点定位（按影响排序）

**热点 A：`/codex/status` 轮询路径（parseCodexStatus）—— 每 1.4s 全量重读**
- 发送消息后前端每 1.4s 轮询一次，每次请求都执行：
  `readTailLines(file)`（读 5MB 尾部 + 全量 JSON.parse 全部行）→ 多次线性遍历（since 定位、task_started 定位、turn 过滤、context/model/reasoning 统计）。
- 单次成本：5MB 日志约 5k~20k 行 JSON.parse + 5~6 次数组遍历，约 10~60ms（视日志行数与行大小）。
- 结论：**全链路最大 CPU 热点**，但当前 1.4s 间隔下 CPU 占用仍可接受（单用户场景 <3%）。属"可优化但非紧急"。

**热点 B：`/codex/history` 大文件双重解析**
- `readHistoryLinesAdaptive` 在文件 >48MB 时：先读 8MB 块做 `countCodexHistoryMessages` 预检（全量 JSON.parse 一遍），消息不足再读 128MB 全量；随后 `parseCodexThreadHistory` 又全量 JSON.parse 一遍。
- 最坏情况（128MB 长会话日志）：**同一批行被 JSON.parse 2 遍**，且 `JSON.parse` 前无法通过行首类型快速跳过（需要解析才知道是不是 user_message）。
- 结论：超大日志场景下的延迟瓶颈，属中等风险优化点。

**热点 C：静态资源命中缓存仍同步 stat**
- 每次静态请求（即使 LRU 命中）都先 `fs.statSync` 同步磁盘 I/O。移动端 WebView 每次加载控制台会并行请求十几个图标/字体资源，每请求多一次 syscall。
- 已修复（见 §三）。

**热点 D：`listCodexThreads` 全量扫描会话目录**
- 每个 /codex/threads 请求（前端 4.5s 一次）：`walkFiles` 全目录 + 对每个文件 `statSync` + 64KB 头读（meta）+ 512KB 尾读（runtime）。命中缓存时仍有每文件 2 次 syscall + 头读。
- 100 个会话约 200+ 次 syscall / 请求。有 1.2s TTL 兜底，可接受；会话数 >500 时值得做"活跃文件优先"优化。

**热点 E：JSON 回退模式下队列 O(n) 操作（已修复）**
- `enqueue` 每次 `Math.max(...this._queue.map(q => q.id))`：O(n) 全量扫描，且 spread 展开 >10 万项会 RangeError 栈溢出。
- 已修复（见 §三）。

**热点 F：历史附件描述 O(n) 扫描（已修复）**
- `historyAttachmentDescriptor` 对每个附件遍历整个 `historyAttachmentCache`（上限 600 项）找 filePath。
- 已修复（见 §三）。

### 1.3 前端结论

- 轮询定时器（`pollTimer` 1.4s / `autoRefreshTimer` 5s / `threadStateTimer` 4.5s / `routeMonitor` 5s / `runDurationTimer` 1s / `approvalRefreshTimer` 1.4s）全部有停止/防重入路径，且 `document.hidden` 时静默，**无泄漏隐患**。
- `threadMenuVisualSignature` 每 4.5s 对 120 项排序 + 字符串拼接（约 1~2ms），仅用于判断是否重渲染，设计合理。
- scroll/input/pointermove 监听均为轻量坐标计算（长按判定、视口固定），无节流必要；`textarea` input 触发 `autosize()` + `renderSlashCommandMenu()` 均 O(1)。
- 唯一的低效点：`serializeMessages()` 在每次轮询完成时同步写 `localStorage`（每次全量 JSON.stringify 最近 30 条消息）。1.4s 间隔下手机端每次写几十 KB 属可接受，若设备卡顿可降频（仅在最终态写入）。

## 三、本次已实施的低风险修复（3 个文件）

### 3.1 `server.js` — 静态缓存命中跳过 stat（热点 C）

```js
// 命中内存缓存且 TTL 内：跳过磁盘 stat，直接复用（热点静态资源零磁盘 I/O）
const cached = staticFileCache.get(cacheKey);
if (cached && now - cached.checkedAt < STATIC_CACHE_STAT_TTL_MS) { ...直接返回缓存... }
// 到期后仍走 statSync + mtime/size 校验，保证文件更新可感知
```
- `STATIC_CACHE_STAT_TTL_MS = 1000`：静态资源 1s 内不会变更，到期后照常校验，语义安全。
- HTML（`no-store` 不缓存）不受影响；图标/manifest 等更新最多延迟 1s 生效。
- 顺带修复：文件读失败时主动从缓存删除失效条目。

### 3.2 `src/store/queue.js` — JSON 回退模式 enqueue O(1)（热点 E）

- 新增 `this._nextId` 游标替代 `Math.max(...map)`：
  - `_initJsonStore` 加载队列时恢复游标（`max(id)+1`），**避免重启后 ID 重复导致 complete/fail 误操作**；
  - `enqueue` 直接 `const id = this._nextId++`，O(1)。
- SQLite 模式不受影响（`lastInsertRowid` 自增）。

### 3.3 `src/cdp/ws-hub.js` — 状态比较与慢客户端保护（热点 4/5）

- `_pollAndBroadcast`：两次 `JSON.stringify` 比较改为单次 stringify + 文本缓存比较。
- `broadcast` / `_sendToClient`：`socket.writableLength > 512KB` 时 `socket.end()` 并移除客户端——状态推送可容忍丢失，客户端 WebSocket 会自动重连，**防止慢手机客户端导致服务端内存无限增长**。

### 3.4 `server.js` — 历史附件反向索引（热点 F）

- 新增 `historyAttachmentIdByPath`（filePath → id）Map：
  - `historyAttachmentDescriptor` 由 O(n) 扫描 600 项缓存变为 O(1) 直接命中；
  - 缓存淘汰（LRU）、过期失效、`handleHistoryAttachment` 删除路径均同步维护反向索引，**无悬挂条目**。

### 验证结果

- `node --check` × 3 文件：通过。
- 全量测试：**38/38 通过**（改动前 401ms / 改动后 426ms，无回归）。
- HTTP 冒烟测试（临时起服）：`/favicon.png` 首次 200（2620B）、1s 内二次命中缓存 200、`/` 200（397KB）、404 路径正确 → 静态服务改动行为正常。

## 五、结论

- 架构层：缓存分层（静态 LRU / 会话 mtime / 线程列表 TTL / 队列持久化）设计健康，无 O(n²) 全量文件读取、无每次请求读磁盘的路径。
- 已修复 5 处明确低风险问题（3 个文件），全部通过测试与冒烟验证。
- 剩余主要优化空间集中在 `/codex/status` 轮询增量解析（项 6）与历史大文件单遍解析（项 7），均属中等风险、建议后续迭代按 §4.3 顺序实施。
